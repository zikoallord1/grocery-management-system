# التشغيل دون اتصال وسلامة البيانات  نظام إدارة البقالات V1.0

## 1. الغرض

تحدد هذه الوثيقة قواعد التشغيل Offline-First وقواعد سلامة البيانات Data Integrity في نظام إدارة البقالات V1.0.

الهدف:

- استمرار العمليات الأساسية بدون إنترنت.
- حماية البيانات من الفقد أو التكرار.
- ضمان أن العملية التجارية إما تنجح كاملة أو لا تترك أثرا جزئيا.
- منع فساد العلاقات بين المبيعات والمخزون والصندوق والعملاء والموردين.
- دعم النسخ الاحتياطي والاستعادة بشكل آمن.
- توفير أساس قابل للتوسع مستقبلا.

## 2. المبدأ الأساسي

> الإنترنت ليس شرطا لتشغيل الوظائف الأساسية للنظام.

المصدر المحلي للحقيقة هو:

SQLite Local Database

ويجب أن تعمل العمليات الأساسية حتى عند:

- انقطاع الإنترنت.
- عدم وجود شبكة.
- توقف خدمة خارجية.
- عدم توفر اتصال بحساب سحابي.

## 3. حدود Offline V1.0

تعمل محليا دون اتصال:

- البيع.
- الشراء.
- المخزون.
- العملاء.
- الموردون.
- التحصيل.
- السداد.
- المصروفات.
- الصندوق.
- التقارير المحلية.
- المستخدمون والصلاحيات.
- إعدادات النظام.
- المرفقات المحلية.
- النسخ الاحتياطي.
- الاستعادة.
- الترخيص المحلي وفق سياسة الترخيص.

ولا تكون العمليات الأساسية معتمدة على API خارجي.

## 4. المعمارية المحلية

المسار الطبيعي:

UI
 Local Application/API
 Business Engine
 Repository
 SQLite

ولا يسمح بأن تنتظر عملية البيع اتصالا خارجيا حتى تصبح ناجحة.

## 5. قاعدة الذرية Transaction Atomicity

أي عملية تجارية مركبة يجب أن تنفذ داخل Transaction مناسبة.

مثال البيع:

1. التحقق.
2. إنشاء الفاتورة.
3. إنشاء البنود.
4. التحقق النهائي من المخزون.
5. إنشاء حركة المخزون.
6. إنشاء الدفعات.
7. إنشاء حركة الصندوق.
8. إنشاء حركة العميل عند الآجل.
9. إنشاء Audit.
10. Commit.

إذا فشل أحد الأجزاء الإلزامية:

ROLLBACK

ويجب ألا تبقى عملية نصف مكتملة.

## 6. قاعدة النجاح الكامل

العملية تعتبر ناجحة فقط بعد إتمام جميع خطواتها الإلزامية.

قبل Commit:

- العملية غير مكتملة.
- لا يجوز عرضها للمستخدم على أنها مؤكدة.

بعد Commit:

- تصبح العملية معتمدة حسب حالتها.

## 7. الانقطاع أثناء العملية

إذا حدث:

- انقطاع الكهرباء.
- إغلاق التطبيق بالقوة.
- توقف Windows.
- انهيار العملية.
- توقف قاعدة البيانات مؤقتا.

أثناء Transaction:

يجب أن تعتمد SQLite آلية Recovery/Atomic Commit الخاصة بها بحيث:

- لا تبقى العملية نصف مكتوبة.
- لا تنشأ حركة مخزون دون المستند.
- لا تنشأ حركة صندوق دون المستند.
- لا ينشأ رصيد عميل دون مصدر.

## 8. WAL Mode

يفضل استخدام SQLite WAL Mode في بيئة V1.0 عند توافقه مع التشغيل المحلي.

الهدف:

- تحسين الاعتمادية في القراءة/الكتابة المتزامنة.
- تقليل مشاكل القراءة أثناء الكتابة.
- تحسين الأداء في الأجهزة الضعيفة.

ويجب اختبار WAL مع النسخ الاحتياطي والاستعادة قبل اعتماده تشغيليا.

## 9. Foreign Keys

يجب تفعيل SQLite Foreign Keys.

الهدف:

منع:

- بند بيع بلا فاتورة.
- بند شراء بلا فاتورة.
- حركة مخزون بلا صنف.
- حركة عميل بلا عميل.
- حركة مورد بلا مورد.
- حركة صندوق بلا صندوق.
- مرفق بلا سجل مرتبط.

## 10. Constraints

سلامة البيانات تعتمد على:

- PRIMARY KEY
- FOREIGN KEY
- UNIQUE
- NOT NULL
- CHECK

ولا يعتمد النظام على التحقق في الواجهة فقط.

## 11. Idempotency

العمليات الحساسة تستخدم معرفا فريدا لمنع التكرار.

مثال:

Operation ID = UUID

إذا أعيد إرسال نفس العملية:

- يبحث Business Engine عن العملية السابقة.
- إذا كانت مكتملة لا يعيد تنفيذ آثارها.
- يعيد نتيجة العملية الأصلية عند الإمكان.

## 12. الضغط المتكرر على زر الحفظ

إذا ضغط المستخدم حفظ مرتين:

يجب ألا يؤدي ذلك إلى:

- فاتورتين.
- حركتي مخزون.
- حركتي صندوق.
- حركتي عميل.
- قيدين مكررين.

الواجهة تمنع الإرسال المزدوج لكن الحماية الأساسية تكون في Application/Business/Database Layers.

## 13. العمليات المتكررة بعد إعادة التشغيل

إذا أغلق البرنامج بعد تنفيذ عملية ولم يعرف المستخدم هل نجحت أم لا:

لا يعاد إنشاء العملية يدويا قبل التحقق.

البرنامج يجب أن يبحث عن:

- idempotency_key.
- رقم المستند.
- حالة العملية.

ثم يقرر:

- موجودة ومكتملة  إرجاع النتيجة.
- غير موجودة  تنفيذها.
- موجودة بحالة غير مكتملة وفق التصميم  معالجة حالة الاسترداد.

## 14. حالات العمليات

يجب أن تكون حالات العمليات واضحة مثل:

- DRAFT
- PROCESSING
- CONFIRMED
- FAILED
- CANCELLED

ولا تستخدم حالة واحدة مبهمة لكل الحالات.

## 15. قاعدة عدم وجود آثار جزئية

مثال ممنوع:

Sale Exists = نعم
Stock Movement = لا

أو:

Sale Exists = نعم
Cash Movement = لا

أو:

Customer Credit = نعم
Sale = لا

إلا إذا كانت الحالة مؤقتة ضمن Transaction لم يتم Commit بها ولا تعرض للمستخدم كعملية مكتملة.

## 16. سلامة المخزون

Stock Movements هي مصدر الحقيقة.

يجب منع:

- حركتين ناتجتين عن نفس العملية.
- حركة بلا مصدر.
- حركة مرتبطة بصنف غير موجود.
- كمية غير منطقية.

يمكن استخدام Stock Balance كـ Cache فقط.

## 17. سلامة الصندوق

Cashbox Movements هي مصدر الحقيقة.

كل زيادة أو نقصان يجب أن يكون قابلا للتتبع.

لا يجوز:

- تعديل الرصيد يدويا دون حركة.
- إنشاء حركة بلا مصدر.
- تسجيل قبض مضاعف بسبب إعادة المحاولة.

## 18. سلامة حسابات العملاء

Customer Account Movements هي مصدر الحقيقة.

لا يجوز:

- تغيير رصيد العميل مباشرة.
- إنشاء حركة حساب بلا مصدر.
- تسجيل تحصيل مرتين.

## 19. سلامة حسابات الموردين

Supplier Account Movements هي مصدر الحقيقة.

لا يجوز:

- تغيير رصيد المورد مباشرة.
- إنشاء حركة بلا مصدر.
- تسجيل سداد مرتين.

## 20. سلامة المرفقات

المرفقات تحفظ محليا.

يجب التحقق من:

- اسم الملف.
- المسار.
- نوع الملف.
- الحجم.
- checksum عند الحاجة.

إذا كان الملف مفقودا لا يجب أن يؤدي فتح السجل إلى انهيار النظام.

يعرض النظام أن المرفق غير متاح مع بقاء السجل الأصلي سليما.

## 21. التخزين المحلي

يجب فصل:

### Database
بيانات SQLite.

### Attachments
الملفات المرتبطة بالسجلات.

### Backups
النسخ الاحتياطية.

### Logs
السجلات التقنية عند الحاجة.

ولا تحفظ الملفات الحساسة عشوائيا داخل مجلدات المصدر البرمجي.

## 22. النسخ الاحتياطي

يجب أن يدعم النظام نسخا احتياطية محلية.

أنواع النسخ:

- Manual Backup.
- Automatic Backup عند النقاط المحددة.
- Pre-Restore Backup قبل تنفيذ Restore.

## 23. قاعدة النسخة قبل الاستعادة

قبل Restore:

1. التحقق من ملف النسخة.
2. إنشاء Backup للبيانات الحالية.
3. التأكد من إمكانية العودة إلى الحالة السابقة.
4. تنفيذ الاستعادة.
5. فحص قاعدة البيانات.
6. تشغيل Integrity Checks.
7. تسجيل العملية في Audit/System Log.

## 24. التحقق من النسخة الاحتياطية

لا يكفي وجود ملف Backup.

يجب التحقق من:

- وجود الملف.
- حجمه.
- سلامته.
- قابلية فتح SQLite.
- سلامة الجداول الأساسية.
- سلامة العلاقات.
- قابلية القراءة.

عند الإمكان ينفذ النظام Restore Test على نسخة مؤقتة دون تدمير البيانات الحالية.

## 25. تسمية النسخ

يفضل أن يحتوي اسم النسخة على:

- اسم النظام.
- التاريخ.
- الوقت.
- نوع النسخة.

مثال:

grocery_backup_20260914_193000.db

## 26. الاحتفاظ بالنسخ

يجب أن تكون سياسة الاحتفاظ قابلة للإعداد مثل:

- آخر 5 نسخ.
- آخر 10 نسخ.
- أو مدة زمنية محددة.

ولا يحذف النظام النسخة الوحيدة المتبقية.

## 27. النسخ التلقائي

V1.0 يمكن أن يدعم النسخ التلقائي وفق إعداد قابل للضبط.

نقاط النسخ المحتملة:

- عند إغلاق اليوم.
- قبل Restore.
- قبل تحديث نسخة التطبيق.
- وفق فترة زمنية محددة.

ولا يجب أن يؤدي فشل النسخ التلقائي إلى فقد العملية التجارية الأصلية.

## 28. Restore

Restore عملية إدارية حساسة.

تتطلب:

- صلاحية مناسبة.
- تأكيدا واضحا.
- Backup قبل الاستعادة.
- تحققا من النسخة.
- تسجيل Audit.

بعد الاستعادة:

- يعاد تحميل حالة النظام.
- يتم التحقق من سلامة قاعدة البيانات.
- يراجع رقم الإصدار/schema version.

## 29. Schema Version

قاعدة البيانات يجب أن تحتوي على إصدار Schema.

مثال:

schema_version

وعند تطوير نسخة جديدة:

- Migration رقمية.
- قابلة للتتبع.
- لا تعتمد على تعديل يدوي عشوائي للقاعدة.

## 30. Migrations

أي تغيير في بنية قاعدة البيانات ينفذ عبر Migration موثقة.

مثال:

V1  V2

ولا يجب أن يقوم التطبيق بتغيير الجداول بطريقة غير قابلة للتتبع عند التشغيل.

## 31. فشل Migration

إذا فشلت Migration:

- لا يكمل النظام بصورة غير معروفة.
- يسجل سبب الخطأ.
- يمنع الاستخدام غير الآمن.
- يحافظ على نسخة احتياطية قبل التغيير متى أمكن.

يجب اختبار Rollback أو Recovery Strategy لكل Migration حساسة.

## 32. التزامن المحلي

V1.0 مصمم أساسا كتطبيق محلي.

لا يفترض وجود عدة أجهزة تتعامل مع نفس قاعدة SQLite عبر شبكة غير موثوقة.

إذا احتاج المنتج مستقبلا إلى تعدد الأجهزة يتم تصميم ذلك كإضافة معمارية مستقلة.

## 33. قفل العمليات

يجب منع تنفيذ عمليتين متعارضتين على نفس السجل في اللحظة نفسها بطريقة تؤدي إلى:

- بيع نفس الكمية مرتين.
- خصم رصيد العميل مرتين.
- تعديل نفس العملية بشكل متناقض.

ويستخدم Database/Application locking المناسب حسب العملية.

## 34. التحقق بعد الكتابة

بعد Commit للعمليات الحساسة:

يجب أن تكون النتيجة قابلة للتحقق.

مثال البيع:

- الفاتورة موجودة.
- مجموع البنود صحيح.
- المخزون نقص مرة واحدة.
- الدفع مسجل.
- العميل سجل فقط الجزء الآجل.
- Audit موجود.

## 35. Integrity Checks

يجب أن يحتوي النظام على وظائف تحقق داخلية عند الحاجة لاكتشاف:

- حركات بلا مصادر.
- بنود بلا رؤوس.
- مستندات بأرقام مكررة.
- أرصدة مشتقة لا تتفق مع الحركات.
- ملفات مرفقات مفقودة.
- علاقات Foreign Keys غير سليمة.

## 36. SQLite Integrity Check

يجب اختبار:

PRAGMA integrity_check;

عند عمليات الصيانة أو الاختبار المناسبة.

يجب ألا يعتمد التشغيل اليومي على تشغيل فحص كامل بعد كل عملية بسبب التكلفة.

## 37. Foreign Key Check

عند الفحص والصيانة:

PRAGMA foreign_key_check;

ويجب أن تكون النتيجة خالية من المخالفات قبل اعتماد نسخة سليمة.

## 38. التعامل مع أخطاء قاعدة البيانات

إذا ظهر خطأ Database:

- لا يخفي النظام الخطأ.
- لا يعرض نجاحا كاذبا.
- يسجل الخطأ تقنيا.
- يعيد Transaction عند الحاجة.
- يوضح للمستخدم أن العملية لم تعتمد إذا لم يحدث Commit.

## 39. التعامل مع امتلاء القرص

قبل عمليات الكتابة المهمة يمكن التحقق من مساحة التخزين عند الحاجة.

إذا كانت المساحة غير كافية:

- تمنع العملية قبل إتلاف البيانات.
- يظهر تنبيه واضح.
- لا يتم تسجيل العملية كناجحة.

## 40. التعامل مع تلف قاعدة البيانات

إذا فشل SQLite Integrity Check:

- يوقف النظام العمليات الحساسة.
- لا يحاول إصلاح البيانات بصمت.
- يطلب إجراء صيانة/استعادة.
- يحتفظ بنسخة البيانات الحالية إن أمكن.
- يسجل الحالة.

## 41. السجل التقني

بالإضافة إلى Audit Business يمكن وجود Technical Log لتسجيل:

- استثناءات التطبيق.
- فشل Transactions.
- مشاكل قاعدة البيانات.
- مشاكل Backup/Restore.
- مشاكل Migration.

ويجب عدم وضع كلمات مرور أو أسرار حساسة داخل السجلات.

## 42. عدم تسجيل الأسرار

لا يجوز تسجيل:

- كلمات المرور.
- مفاتيح التشفير.
- رموز الترخيص السرية.
- أسرار النظام.

بصيغتها الصريحة داخل Logs.

## 43. التشفير

V1.0 لا يفترض تشفير قاعدة SQLite كاملة إلا إذا تم اعتماده كمتطلب صريح.

لكن يجب حماية:

- ملفات المستخدمين.
- بيانات الترخيص.
- كلمات المرور باستخدام Hash آمن.
- صلاحيات الوصول إلى ملفات النظام.

## 44. كلمة المرور

لا تخزن كلمة مرور المستخدم نصا صريحا.

يجب استخدام password_hash مع خوارزمية مناسبة.

## 45. إغلاق البرنامج

عند الإغلاق الطبيعي:

- إنهاء العمليات الجارية.
- Commit أو Rollback للمعاملات المفتوحة.
- تحرير الموارد.
- إغلاق الاتصالات.

ولا يعتمد النظام على الإغلاق الطبيعي وحده لضمان سلامة البيانات SQLite Transactions هي الحماية الأساسية.

## 46. إغلاق البرنامج بالقوة

عند Force Close أو crash:

بعد إعادة التشغيل:

- يفحص التطبيق حالة قاعدة البيانات.
- يعتمد على Recovery الداخلي لقاعدة البيانات.
- لا يعيد العمليات القديمة تلقائيا دون Idempotency/Recovery Rules.
- يعرض حالة العملية إذا كانت غير محسومة.

## 47. انقطاع الكهرباء

النظام مصمم بحيث لا يعتمد على بقاء الكهرباء أثناء Commit.

يفضل استخدام جهاز UPS مستقبلا عند الحاجة لكن عدم وجود UPS لا يبرر تصميما يسمح بنصف عملية.

## 48. سلامة البيانات عند الطباعة

الطباعة لا تنشئ عملية مالية.

طباعة فاتورة:

- تقرأ المستند.
- لا تنقص المخزون.
- لا تقبض المال.
- لا تضيف حركة جديدة.

## 49. سلامة البيانات عند Preview

Preview للفاتورة أو التقرير:

- قراءة فقط.
- لا تعديل.
- لا إنشاء حركة.

## 50. سلامة البيانات عند Export

Export إلى:

- PDF.
- Excel.
- CSV.

يجب أن يكون عملية قراءة فقط.

فشل Export لا يعني فشل العملية التجارية الأصلية.

## 51. النسخ الاحتياطي والمرفقات

عند اعتماد Backup شامل:

يجب تحديد هل النسخة تشمل:

- Database.
- Attachments.
- Settings.
- License Information.

والافتراضي في النظام التجاري:

> Backup شامل للبيانات المطلوبة لاستعادة حالة العمل وليس قاعدة البيانات وحدها إذا كانت المرفقات جزءا من السجل التشغيلي.

## 52. Checksum

يمكن استخدام checksum للتحقق من:

- سلامة المرفقات.
- سلامة ملفات النسخ.
- اكتشاف التعديل غير المتوقع.

## 53. استعادة المرفقات

إذا تمت استعادة قاعدة بيانات دون ملفات المرفقات:

- تظهر السجلات.
- يظهر أن المرفق غير متوفر.
- لا ينهار النظام.
- يسجل تحذيرا.

أما Restore الكامل فيجب أن يعيد قاعدة البيانات والمرفقات المتوافقة مع النسخة.

## 54. قاعدة التوافق بين Database وAttachments

يفضل أن يكون لكل نسخة Backup معرف إصدار/لقطة Snapshot يربط:

Database
+
Attachments

حتى لا تتم استعادة قاعدة من زمن مختلف عن الملفات.

## 55. Offline Reporting

التقارير الأساسية يجب أن تعمل من البيانات المحلية.

لا يعتمد تقرير:

- المبيعات اليومية.
- المشتريات.
- المخزون.
- العملاء.
- الموردين.
- المصروفات.
- الصندوق.

على اتصال خارجي.

## 56. Search Offline

البحث الأساسي يعمل محليا:

- اسم الصنف.
- الباركود.
- الكود.
- العميل.
- المورد.
- رقم المستند.

ولا يعتمد على خدمة بحث خارجية.

## 57. الترخيص Offline

الترخيص الأساسي يجب أن يكون قابلا للتحقق محليا وفق السياسة المعتمدة.

إذا احتاج التحقق الخارجي مستقبلا:

- لا يعطل العمليات المصرح بها دون سياسة واضحة.
- يحتفظ النظام بآخر حالة ترخيص صالحة وفق قواعد الترخيص.

## 58. النسخ قبل الترقية

قبل تحديث إصدار التطبيق أو Schema:

يجب إنشاء Backup مناسب.

إذا فشل التحديث:

- لا يستخدم النظام قاعدة غير متوافقة.
- يمكن العودة إلى النسخة السابقة وفق خطة Recovery.

## 59. Data Integrity Checklist

قبل اعتماد إصدار:

- Foreign Keys تعمل.
- Unique Constraints تعمل.
- Transactions تعمل.
- Rollback يعمل.
- Idempotency يعمل.
- Backup يعمل.
- Restore يعمل.
- Integrity Check يعمل.
- Foreign Key Check يعمل.
- Migrations تعمل.
- لا توجد عمليات مالية جزئية.
- لا توجد أرصدة تتغير دون حركات.

## 60. سيناريوهات الاختبار الحرجة

يجب اختبار:

1. حفظ بيع.
2. انقطاع أثناء الحفظ.
3. إعادة تشغيل البرنامج.
4. إعادة إرسال نفس البيع.
5. فشل إنشاء حركة المخزون.
6. فشل إنشاء حركة الصندوق.
7. فشل تسجيل العميل.
8. بيع آجل.
9. بيع مختلط.
10. مرتجع.
11. شراء.
12. مصروف.
13. Restore.
14. Restore مع نسخة تالفة.
15. Migration.
16. امتلاء القرص.
17. ملف مرفق مفقود.
18. قاعدة بيانات بها Foreign Key مشكلة.
19. فتح البرنامج بعد Crash.
20. إغلاق التطبيق بالقوة.

## 61. معيار نجاح الاستعادة

بعد Restore ناجح يجب أن تكون حالة النظام متسقة:

- المبيعات موجودة.
- المشتريات موجودة.
- المخزون متوافق.
- أرصدة العملاء متوافقة.
- أرصدة الموردين متوافقة.
- حركات الصندوق متوافقة.
- المصروفات موجودة.
- المرفقات موجودة إذا كانت ضمن النسخة.
- إعدادات النظام متوافقة.

## 62. مبدأ عدم فقدان البيانات الصامت

لا يجوز للنظام أن:

- يسقط عملية دون تنبيه.
- يحذف سجلا بسبب خطأ داخلي.
- يستبدل نسخة صحيحة بأخرى تالفة دون تحذير.
- يعلن نجاح Backup لم يتم إنشاؤه بنجاح.
- يعلن نجاح Restore قبل التحقق.

## 63. قاعدة إبلاغ المستخدم

رسائل سلامة البيانات يجب أن تكون واضحة.

مثال:

"تم حفظ العملية بنجاح."

أو:

"لم يتم اعتماد العملية بسبب خطأ ولم يتم تسجيل أثر مالي."

ولا تستخدم رسالة نجاح إذا كان Commit لم يتم.

## 64. النسخة الآمنة

أي Backup يعلن النظام نجاحه يجب أن:

- يكون موجودا.
- يكون قابلا للقراءة.
- يمر بالتحقق الأساسي.
- يسجل وقت إنشائه.
- يسجل نوعه.

## 65. حالة الوثيقة

هذه الوثيقة تمثل:

OFFLINE & DATA INTEGRITY V1.0  DESIGN BASELINE

وهي المرجع الإلزامي لقواعد:

- Offline-First.
- Transactions.
- Idempotency.
- Backup.
- Restore.
- Migrations.
- Integrity Checks.
- Crash Recovery.
- Data Consistency.

ولا يجوز بدء التنفيذ الفعلي لهذه الأجزاء قبل ربطها باختبارات قبول واضحة.

## 66. قاعدة النسخ الآمن لقاعدة SQLite وWAL

عند تفعيل SQLite WAL Mode لا يعتبر نسخ ملف قاعدة البيانات الرئيسي وحده أثناء وجود عمليات كتابة طريقة Backup موثوقة تلقائيا.

يجب أن ينفذ Backup باستخدام آلية متوافقة مع SQLite Backup API أو آلية آمنة مكافئة تضمن لقطة متسقة لقاعدة البيانات.

وعند الحاجة إلى الاعتماد على ملف قاعدة البيانات وملفات WAL المرتبطة به يجب أن يتعامل النظام مع المجموعة كاملة وفق آلية النسخ المعتمدة وألا يعلن نجاح النسخة بناء على نسخ ملف واحد فقط.

بعد إنشاء النسخة:

1. يتم التحقق من وجودها.
2. يتم التحقق من إمكانية فتحها.
3. يتم تنفيذ Integrity Check على نسخة الاختبار عند الإمكان.
4. لا تعتبر النسخة ناجحة إلا بعد اجتياز التحقق الأساسي.

ولا يجوز تنفيذ Checkpoint أو أي عملية صيانة لـ WAL بشكل عشوائي أثناء عملية Backup بل يجب أن تكون جزءا من استراتيجية Backup المعتمدة والمختبرة.

الهدف النهائي:

> Backup صحيح ومتسق وقابل للاستعادة وليس مجرد نسخة من ملف SQLite.

## 67. قرار اعتماد Backup V1.0

القاعدة المعتمدة في V1.0:

- استخدام آلية SQLite Backup آمنة عند تنفيذ النسخ البرمجي.
- عدم الاعتماد على File Copy خام لملف SQLite أثناء التشغيل كآلية Backup نهائية.
- اختبار Backup وRestore فعليا قبل اعتماد المنتج.
- التحقق من النسخة بعد إنشائها.
- إنشاء Backup قبل Restore وقبل التغييرات البنيوية الحساسة.
