# نظام إدارة البقالات V1.0
# وثيقة المعمارية التقنية Architecture
# الإصدار: V1.0

## 1. الهدف

هذه الوثيقة تحدد المعمارية التقنية الرسمية لنظام إدارة البقالات V1.0 قبل بدء البرمجة.

الأهداف:

- العمل بالكامل دون الحاجة إلى الإنترنت للعمليات الأساسية.
- سرعة التشغيل على أجهزة Windows محدودة الإمكانات.
- سهولة الاستخدام.
- حماية العمليات المالية.
- النسخ الاحتياطي والاستعادة.
- قابلية التثبيت التجاري.
- قابلية التوسع مستقبلا.

## 2. المبدأ الأساسي

المستخدم ينفذ العملية التجارية مرة واحدة والنظام ينفذ تلقائيا جميع الآثار المرتبطة بها.

المسار العام:

Business Event
 Rule
 Engine
 Inventory / Cash / Accounts
 Reports
 Audit

## 3. النمط المعماري

يعتمد V1.0 على:

**Modular Monolith**

أي تطبيق واحد متكامل مقسم داخليا إلى وحدات واضحة.

السبب:

- أبسط في التثبيت.
- أقل استهلاكا للموارد.
- مناسب للعمل دون إنترنت.
- أسهل في الصيانة.
- مناسب لجهاز عميل واحد.
- يسمح بالتوسع مستقبلا.

لا تستخدم Microservices في V1.0 لأنها تضيف تعقيدا غير ضروري.

## 4. الطبقات

### Presentation Layer

مسؤولة عن:

- الواجهة.
- التنقل.
- إدخال البيانات.
- البحث.
- Smart Fields.
- الاختصارات.
- الطباعة.

ولا تحتوي على منطق الأعمال الأساسي.

### Application Layer

تنظم حالات الاستخدام مثل:

- إنشاء بيع.
- إنشاء شراء.
- قبض من عميل.
- دفع لمورد.
- تسجيل مصروف.
- تسجيل مرتجع.
- إغلاق اليوم.

وتتحقق من الصلاحيات وتنسق التنفيذ.

### Domain / Business Engine

تحتوي على:

- قواعد البيع.
- قواعد الشراء.
- قواعد المخزون.
- قواعد الصندوق.
- قواعد العملاء.
- قواعد الموردين.
- قواعد المصروفات.
- قواعد المرتجعات.
- قواعد الإلغاء.
- القواعد المالية.

### Data Access Layer

مسؤولة عن:

- القراءة.
- الحفظ.
- التحديث.
- الاستعلامات.
- Transactions.
- الفهارس.

ولا تحتوي على منطق الأعمال الرئيسي.

### Database Layer

قاعدة البيانات المحلية هي مصدر الحقيقة الرئيسي.

## 5. قاعدة البيانات

الاختيار الأساسي لـ V1.0:

**SQLite**

لأنها:

- محلية.
- لا تحتاج إلى خادم.
- تعمل دون إنترنت.
- قليلة استهلاك الموارد.
- سهلة النسخ الاحتياطي.
- مناسبة للتطبيق المحلي.

ويجب تصميم النظام بحيث يمكن الانتقال مستقبلا إلى PostgreSQL عند الحاجة إلى تعدد الفروع أو خادم مركزي.

## 6. Transaction Integrity

العمليات الحساسة تنفذ داخل Transaction متماسكة.

مثال البيع:

1. التحقق من البيانات.
2. التحقق من الصلاحيات.
3. حفظ الفاتورة.
4. حفظ تفاصيلها.
5. تحديث المخزون.
6. تحديث حساب العميل عند البيع الآجل.
7. تحديث الصندوق عند القبض.
8. تسجيل الأثر المالي.
9. تسجيل Audit Log.
10. Commit.

إذا فشل جزء أساسي يتم Rollback.

الهدف:

> لا توجد فاتورة ناجحة مع مخزون غير محدث.

## 7. Business Events

أمثلة:

- SALE_CREATED
- SALE_CANCELLED
- SALE_RETURNED
- PURCHASE_CREATED
- PURCHASE_CANCELLED
- PURCHASE_RETURNED
- CUSTOMER_PAYMENT
- SUPPLIER_PAYMENT
- EXPENSE_CREATED
- STOCK_ADJUSTMENT
- DAY_CLOSED

كل حدث يمر عبر قواعد العمل قبل تنفيذ آثاره.

## 8. المخزون

لا يتم تعديل المخزون مباشرة من الواجهة.

مصادر الحركة:

- شراء.
- بيع.
- مرتجع بيع.
- مرتجع شراء.
- تسوية مصرح بها.
- هالك عند دعم الوظيفة.
- افتتاح المخزون.

كل حركة يجب أن تكون مرتبطة بمصدرها.

## 9. الصندوق

الصندوق يعتمد على سجل حركات.

أمثلة:

- قبض من بيع.
- قبض من عميل.
- دفع لمورد.
- مصروف.
- سحب.
- إيداع.
- تسوية مصرح بها.

لا يتم تعديل الرصيد يدويا دون حركة مبررة.

## 10. العملاء

حساب العميل يتكون من:

- البيع الآجل.
- القبض.
- المرتجع.
- التسويات المصرح بها.

لا يتم تعديل رصيد العميل مباشرة.

## 11. الموردون

حساب المورد يتكون من:

- المشتريات الآجلة.
- الدفع.
- مرتجع الشراء.
- التسويات المصرح بها.

لا يتم تعديل رصيد المورد مباشرة.

## 12. الآثار المالية

المسار:

Business Event
 Accounting Rule
 Financial Effect

لا يوضع المنطق المحاسبي الأساسي داخل شاشة البيع أو الشراء.

## 13. Smart Fields

Smart Fields طبقة مشتركة يعاد استخدامها في جميع أجزاء النظام.

المسار:

Smart Field
 Search Adapter
 Data Source
 Matching
 Ranking
 Suggestions
 Selection
 Auto Fill
 Validation

تستخدم في:

- الأصناف.
- العملاء.
- الموردين.
- المصروفات.
- البحث العام.
- التقارير.

ولا تتخذ قرارات مالية غير مصرح بها.

## 14. البحث

يوجد:

### بحث عام

يبحث في السجلات الرئيسية.

### بحث سياقي

يبحث داخل الشاشة الحالية حسب نوع البيانات المطلوبة.

## 15. الصلاحيات

الصلاحيات تطبق على مستويين:

1. الواجهة.
2. طبقة التطبيق ومحرك الأعمال.

إخفاء الزر وحده ليس حماية.

## 16. Audit Trail

تسجل العمليات الحساسة:

- المستخدم.
- العملية.
- السجل المتأثر.
- التاريخ والوقت.
- النتيجة.
- المعرف الفريد للعملية.
- سبب الإلغاء أو التصحيح عند الحاجة.

## 17. عدم الحذف المالي

لا يتم حذف العمليات المالية المعتمدة نهائيا.

البدائل:

- الإلغاء.
- العكس.
- المرتجع.
- التصحيح المصرح به.

ويجب الحفاظ على قابلية التتبع.

## 18. Idempotency

العمليات الحساسة تستخدم معرفا فريدا مثل UUID لمنع تنفيذ نفس العملية مرتين بسبب:

- الضغط المتكرر.
- إعادة الإرسال.
- أخطاء الواجهة.
- استعادة العملية بعد فشل.

## 19. Offline First

العمليات الأساسية تعمل دون إنترنت:

- البيع.
- الشراء.
- المخزون.
- العملاء.
- الموردون.
- المصروفات.
- الصندوق.
- التقارير.
- النسخ الاحتياطي.

الإنترنت ليس شرطا للتشغيل الأساسي.

## 20. النسخ الاحتياطي

يجب توفير:

- نسخة يدوية.
- نسخة تلقائية.
- أكثر من إصدار.
- فحص سلامة النسخة.
- استعادة آمنة.

لا تحفظ كلمات المرور أو الأسرار كنص مكشوف داخل النسخ الاحتياطية.

## 21. الاستعادة

قبل الاستعادة:

1. تحذير المستخدم.
2. فحص النسخة.
3. أخذ نسخة من الحالة الحالية عند الإمكان.
4. إغلاق العمليات المفتوحة.
5. تنفيذ الاستعادة.
6. فحص سلامة قاعدة البيانات.
7. تسجيل العملية.

## 22. الإعدادات

تكون الإعدادات مركزية وتشمل:

- اسم البقالة.
- الشعار.
- العملة.
- الفواتير.
- الطباعة.
- الباركود.
- المخزون.
- الصندوق.
- النسخ الاحتياطي.
- المستخدمين.
- الصلاحيات.
- الترخيص.

## 23. التقارير

التقارير تقرأ البيانات المعتمدة ولا تعدل:

- المخزون.
- الصندوق.
- الحسابات.

التقارير للعرض والتحليل والتصدير.

## 24. المرفقات

يمكن ربط المرفقات بالسجلات مثل:

- فاتورة شراء.
- مصروف.
- مستند داعم.

المرفق مرتبط بالسجل الأصلي ولا يمثل بديلا عنه.

## 25. الأمان

الحد الأدنى:

- تخزين آمن لكلمات المرور.
- صلاحيات واضحة.
- Audit Trail.
- التحقق من المدخلات.
- منع SQL Injection.
- عدم تخزين الأسرار داخل الكود.
- عدم رفع بيانات العميل الحقيقية إلى Git.

- استخدام فهارس مناسبة.
- استعلامات محسنة.
- Pagination.

- تقليل العمليات الخلفية.

- عدم استخدام خدمات غير ضرورية.

## 30. التشغيل النهائي

المستخدم النهائي لا يحتاج إلى:

- Python.
- Node.js.
- Terminal.
- إعداد قاعدة البيانات يدويا.

كل ذلك يجب أن يجهزه Installer.

## 31. Installer

التدفق النهائي:

Setup

- التطبيق.

- الاختصارات.
- الملفات المطلوبة.
- الإعداد الأولي.

## 32. فصل التطوير عن المنتج

- Source Code.
- Tests.

- Application.
- Database.
- Configuration.
- Backups.

انتهاء الترخيص لا يؤدي إلى تلف بيانات العميل.

سيتم تفصيل الترخيص في وثيقة مستقلة.

- Unit Tests.
- Integration Tests.
- Acceptance Tests.
- Regression Tests.

يجب توفير بيانات تجريبية آمنة وقابلة لإعادة الإنشاء دون تكرار غير مرغوب.

تشمل:

- أصناف.
- عملاء.
- موردين.
- مشتريات.
- مبيعات.
- دفعات.
- مصروفات.

## 36. قابلية التوسع

يمكن مستقبلا إضافة:

- تعدد الفروع.
- PostgreSQL.
- المزامنة.
- تطبيق جوال.
- خدمات خارجية.
- تقارير متقدمة.

دون إعادة بناء كامل النظام.

لكن لا يضاف التعقيد قبل الحاجة الفعلية.

## 37. القرارات المعمارية الأساسية

لا يجوز كسر المبادئ التالية دون مراجعة التصميم:

1. Offline-first.
2. SQLite في V1.0.
3. Modular Monolith.
4. Business Engine مركزي.
5. فصل الواجهة عن منطق الأعمال.
6. عدم تنفيذ SQL تجاري مباشر من الواجهة.
7. عدم الحذف المالي المباشر.
8. Audit Trail.
9. Idempotency.
10. Smart Fields كطبقة مشتركة.
11. Transactions للعمليات المتماسكة.
12. صلاحيات على مستوى النظام.
13. Installer للمستخدم النهائي.
14. عدم رفع بيانات العملاء الحقيقية إلى Git.

## 38. منع الانحراف أثناء البرمجة

إذا ظهرت حاجة جديدة:

1. تسجل الحاجة.
2. يحدد تأثيرها.
3. تعدل وثيقة التصميم عند الحاجة.
4. تراجع آثارها على قاعدة البيانات والقواعد والاختبارات.
5. ثم تنفذ.

لا يتم تجاوز التصميم بحلول مؤقتة تتحول لاحقا إلى بنية يصعب صيانتها.

 Profit
